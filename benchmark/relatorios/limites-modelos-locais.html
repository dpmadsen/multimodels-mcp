Teste 4 em detalhe — o mais difícil (código de datas)

Pedi uma função que conta dias entre duas datas "DD/MM/AAAA", devolvendo null pra data inválida — com armadilhas: 31/04 não existe, 29/02/2023 não existe, 1900 não é bissexto (regra dos séculos), e o construtor Date do JavaScript aceita datas erradas "rolando" pro mês seguinte.

DeepSeek Flash — 12/12 aprovado

// Estratégia: tabela de dias por mês
// + cálculo manual de ano bissexto
const daysInMonth = [31,28,31,...];
if (year % 400 === 0 ||
   (year % 4 === 0 && year % 100 !== 0)) {
  daysInMonth[1] = 29;
}
if (day < 1 || day > daysInMonth[month-1])
  return null;

Qwen 3.6 — 12/12 aprovado

// Estratégia mais elegante: cria a
// data e confere se ela "rolou".
// Se 31/04 virou 01/05, era inválida.
const d = new Date(Date.UTC(yyyy, mm-1, dd));
if (d.getUTCFullYear() !== yyyy ||
    d.getUTCMonth() !== mm-1 ||
    d.getUTCDate() !== dd) return null;
Os dois passaram nos 12 casos, incluindo os séculos (36.524 dias entre 1900 e 2000). A solução do Qwen usa a própria pegadinha do JavaScript como detector — código que muito programador júnior não escreveria.

Onde estão, então, os limites do Qwen 3.6?

A prova difícil mostrou que o limite dele não é inteligência — é fôlego:

1 · Gasta tokens absurdos "pensando"

Pra calcular 3 porcentagens (4 linhas de resposta), ele consumiu 12.152 tokens de raciocínio interno. O DeepSeek Flash resolveu o mesmo com 184. Isso significa respostas lentas e risco constante de estourar o limite de tamanho.

2 · Provas compostas quebram ele

Na prova anterior (3 questões num pedido só), ele entregou resposta cortada ou vazia em 3 tentativas. Hoje, com as mesmas dificuldades divididas em pedidos pequenos, gabaritou. Regra prática: uma tarefa por vez, bem focada.

3 · Depende do Celta estar de pé

A primeira rodada de hoje falhou porque o servidor da rede estava fora; voltou e funcionou. Modelo local via rede = mais um elo que pode falhar.

Gemma 4 31B — reprovado por WO (por enquanto) fica pra depois

Todas as delegações estouraram o tempo de espera. A investigação direta mostrou o motivo provável:

• O servidor do Celta responde normalmente e o modelo está lá no catálogo.
• Num pedido direto de aquecimento, ele respondeu — mas levou 12 segundos pra gerar meros 20 tokens.
• Descoberta: esse Gemma também é um modelo "pensador" (devolve o raciocínio num campo separado), e é um modelo denso de 31B — o computador inteiro trabalha em cada palavrinha. Já o Qwen 35B é do tipo "esperto" (MoE): só ativa uma fração de si por vez, por isso voa.

Tradução: no hardware atual do Celta, o Gemma 31B pensa devagar demais pro tempo de espera do nosso garçom. Pra ele entrar na próxima prova, o caminho é aumentar o tempo de espera configurável do servidor multimodels (a tarefa de correção dos modelos pensadores, que já está rodando, ataca exatamente essa região do código) ou desligar o modo "pensador" dele no LM Studio.

Veredito prático

✅ Qwen 3.6 no Celta subiu no conceito: pra tarefas focadas (uma função, um cálculo, uma análise), ele entrega qualidade de nuvem, de graça e sem internet. Só não peça provas compostas até a correção do servidor sair.

⏱️ Gemma 4 31B: em compasso de espera — precisa da correção de timeout/pensadores pra ser avaliado com justiça.

☁️ DeepSeek Flash segue sendo a régua: gabaritou tudo de novo, rápido e gastando pouco. É o plano B perfeito quando o Celta estiver desligado.
